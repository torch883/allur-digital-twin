# Спецификация: методика OEE по сменам и ввод смены

Статус: утверждено к реализации, 08.10.2026. Визуальные правила — в [`DESIGN.md`](../../DESIGN.md). Макет итога модалки — [`mockups/stage-modal.png`](mockups/stage-modal.png).

## 1. Методика (одна для Python и JS)

Колонка «Загрузка, %» в данных кейса равна часам работы / 8 (7,8 → 98%, 7,5 → 94%, 8,0 → 100%), поэтому **одна строка = одна смена (8 ч)**.

- A = часы работы / (8 × `shifts_covered` − плановые остановки, ч). Строки кейса: `shifts_covered = 1`; синтетические суточные строки: 2.
- P = факт / план (сырое значение показываем; в OEE идёт min(P, 1)).
- Q = (факт − брак) / факт; брак в штуках.
- OEE = A × min(P, 1) × Q.
- Округление показа: 1 знак, половина вверх. Python: `Fraction` из целых входов → `Decimal(str)` + `ROUND_HALF_UP`. JS: `Math.round(x * 10 + 1e-9) / 10`. Эталон паритета хранит строки показа.
- Единой «OEE завода» нет — только по паре «участок × смена».
- Журнал простоев к смене не привязывается (ведётся по оборудованию/за сутки).

Ручной пример для тестов: Сварка-1 01.10 = 7,8/8 × 118/120 × 116/118 = **94,25%** (показ 94,3).

## 2. Прогноз плана

- Убрать регрессию/бутстрэп по смешанной синтетической истории и поля `p10/p50/p90/risk_pct` (сервер и `offline-data.js → planForecast()`).
- Новый ответ: `working_days` (по умолчанию 21, `assumption: true`), `shifts_total = 2 × working_days`, `required_per_shift = 5500 / shifts_total`, `pace_per_shift` = min по участкам (Σ факт / Σ `shifts_covered`, только `is_synthetic = false`), `projection`, `gap`, `pace_good_scrap_floor`, `shifts_with_data`.
- Сценарные коэффициенты в карточку плана не входят — только в live-сценарии.
- Инцидент «риск недовыполнения плана» — при `projection < target`.
- `workingDays` — одно клиентское состояние (18–26), его читают прогноз, модалка и «Цена смены». Каждый темп подписан: «среднее по 2 сменам файла» / «эта смена».

## 3. Модалка «Ввести смену» (`frontend/js/shift-input.js`)

- Точка входа: кнопка «+ Смена» в topbar на любом экране и клавиша `S` (не в полях ввода).
- Ввод по Сварке/Окраске/Сборке: план (предзаполнен 120), факт, часы, брак (шт), плановые остановки (мин, 0). «Заполнить 02.10» подставляет данные кейса; чекбокс «Учесть ТО ABB-04 (30 мин)» по умолчанию выключен.
- Расчёт — чистая функция `evaluateShift(rows, {shiftHours: 8, workingDays})`, одинаковая онлайн и офлайн.
- Оцениваются нормативы кейса OEE ≥ 85% и брак ≤ 2%; простой не вводится («не оценивается»).
- Выход: число нарушений; OEE и A/P/Q по участкам; разница выпуска сборки с предыдущими участками; участок с минимумом годных; темп этой смены против `required_per_shift`; «Проверить первым» = худший из A, min(P,1), Q у участка с минимальным OEE; «Цена смены» = потерянные минуты × ставка ₸/ч (ставка — допущение или введённая пользователем).

### Состояния

| Фича | Загрузка | Пусто | Ошибка | Успех | Частично |
|---|---|---|---|---|---|
| Ввод | — | План 120, фокус «Сварка·Факт», «Рассчитать» неактивна до первой полной строки | Красная рамка ячейки + одна строка под таблицей; расчёт по валидным строкам | Макет stage-modal | 1–2 участка: остальные строки серые |
| Итог | — | — | — | «N нарушений»; 0 → зелёное «Смена в норме» + «ближе всего к порогу» | Карточки только введённых участков; «Поток»/«Темп»: «нужны все 3 участка» |
| Блок находок | 3 серые строки | Нет `findings` → блок скрыт | Скрыт | Список | — |
| Карточка темпа | Серый блок | — | «Нет данных кейса» | Нужно / делаем + дни | — |
| Бейдж соединения | «Подключение» | — | Офлайн: серый, не красный | «Live · подключено» | — |

- Метка источника: «Файл 02.10» → «02.10 + правки» → «Продиктовано».
- Шаблон «Проверить первым»: A → «доступность {A}% — потеряно {мин} мин из 480»; P → «темп {P}% — недодано {N} машин»; Q → «качество {Q}% — {брак} шт брака».
- Валидация: часы + остановки/60 > 8 — ошибка; план или факт = 0 — ошибка; P > 105% — предупреждение; брак > факт — ошибка; отрицательное/пустое — ошибка.
- Клавиатура: Tab по строке, Enter = «Рассчитать», принимаются «7,2» и «7.2», Esc закрывает с сохранением ввода, стрелки тура в полях не работают.
- Доступность: ловушка фокуса, рамка фокуса 2px, `aria-live="polite"` для вердикта, возврат фокуса на «+ Смена».

## 4. Экраны

- **Правило иерархии:** вверху любого экрана и списка — данные кейса; симуляция — отдельный подписанный слой ниже.
- **Панель руководителя:** блок находок первым (вместо жёлтой плашки плана), затем KPI-плитка «Ниже 85%: n из 6», карточка темпа. Находки — строки списка с тегами `нарушение` / `риск` / `гипотеза` / `вопрос`, порядок нарушения → риски → вопросы.
- **Схема завода:** в карточке участка и боковой панели «OEE 01.10 x · 02.10 y», ниже 85 — `--bad`; живые счётчики симуляции — `--blue` с подписью «модель»; «Требует внимания»: сначала инциденты кейса, затем «— Симуляция —».

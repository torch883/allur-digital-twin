# ALLUR Цифровой двойник автомобильного завода

Рабочий демонстрационный MVP для Qostanai Industry Hackathon, кейс АО «Группа компаний АЛЛЮР», Demo Day 16 октября 2026 года. Интерфейс на русском: схема завода, панель руководителя, инциденты, прогноз ИИ, калькулятор эффекта и архитектура.

## Запуск за две минуты

Из папки проекта, при установленном Docker:

```sh
docker-compose up --build
```

Современный эквивалент: `docker compose up --build`. Следующие запуски: `docker-compose up`. Откройте **http://localhost:8000**. OpenAPI: **http://localhost:8000/docs**. Первый запуск загружает Python-зависимости и может занять больше двух минут при медленном интернете. Последующие запуски используют готовый образ. Один сервис, база хранится в именованном Docker-томе.

Без Docker, Python 3.11 или новее:

```sh
pip install -r requirements.txt
uvicorn app.main:app --reload
```

В оболочках с поддержкой `&&` это одна команда:

```sh
pip install -r requirements.txt && uvicorn app.main:app --reload
```

Рекомендуется виртуальное окружение. На Windows:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

Для устойчивого показа используйте один процесс без autoreload: `uvicorn app.main:app --host 127.0.0.1 --port 8000`. Несколько workers запускают несколько симуляторов; для этого MVP используйте один worker.

При первом старте автоматически создаётся `data/allur.db`, загружается кейс, генерируется синтетическая история, обучается модель. Следующий старт использует существующую базу и последний снимок. Обновление зависимостей для работы демо не требуется. Docker в среде подготовки не был установлен, поэтому образ не запускался; приложение проверено непосредственным запуском Uvicorn и тестами.

## Пять шагов демонстрации

Кнопка **«Презентация»** последовательно проводит через те же шаги:

1. **Схема завода.** Включите Live-симуляцию. Покажите участки, оборудование, запасы и KPI. Нажатие на участок открывает панель; на оборудование — его карточку. Esc закрывает панель, стрелки влево/вправо переключают участки.
2. **Окраска.** Откройте участок. В кейсе 10 дефектов из 231 изделия, 4,33% при допустимых 2%. Синтетическую историю можно включить отдельно. Покажите предупреждение о методике OEE и неизвестной смене.
3. **Поломка конвейера.** Выберите ×20 и нажмите сценарий. Сборка останавливается сразу. Примерно за 3–4 тика заполняется буфер после окраски; далее ограничиваются окраска и сварка. Точная скорость зависит от моделируемых потерь и шума. Альтернативы: всплеск брака до 8% с замедлением окраски или обнуление склада с последовательным исчерпанием буферов.
4. **Прогноз ИИ.** Покажите вероятности, три фактора, коридор p10/p50/p90 и рекомендации. Кнопка пересчитывает прогноз; обучение модели выполняется на старте, периодический пересчёт — каждые 12 тиков. Оценки не подтверждены на реальных производственных данных.
5. **Эффект для бизнеса.** Измените стоимость простоя и ожидаемое улучшение. Все цены, затраты и рабочие дни — редактируемые допущения. Покажите экономию и простую окупаемость.

**Сбросить** / `POST /api/scenarios/reset` восстанавливает начальную демонстрационную смену и удаляет её снимки/события/инциденты. Исходные таблицы, 60 дней истории и пользовательские статусы исторических инцидентов сохраняются. Сценарии взаимно исключают друг друга: запуск нового сценария сначала сбрасывает предыдущий. Сценарий автоматически включает симуляцию.

Ползунок **«Назад во времени»** показывает сохранённый снимок, включая прежние буферы и статусы. Кнопка **«В эфир»** возвращает текущее состояние. Хранится до 720 последних снимков, примерно 30 минут реального времени. Это отдельная история симулятора, не восстановление точного состояния завода по суточным таблицам кейса.

## Офлайн-режим

Все ресурсы, включая шрифт Inter, находятся в проекте. Внешних запросов интерфейс не делает. При недоступности API открытая страница переключается на встроенный JSON-снимок и локальную симуляцию; появляется бейдж **«Офлайн-режим»**. Сценарии, карточки, инциденты и калькулятор продолжают работать. ML-оценки берутся из сохранённого результата Python-модели, сценарные коэффициенты рассчитываются локально. Обучение sklearn в браузере не выполняется.

Service Worker сохраняет оболочку и статические ресурсы после первого успешного открытия на localhost или HTTPS. Поэтому после первого полного открытия возможна перезагрузка страницы при выключенном сервере. При первом в жизни открытии без работающего сервера загрузить приложение невозможно. Раз в 10 секунд проверяется восстановление API. После восстановления показано серверное состояние; локальные офлайн-действия не записываются задним числом в серверную базу.

`localStorage` и `sessionStorage` не используются. Временное состояние офлайн-симуляции хранится в памяти; только статические файлы сохраняются через Cache API. Если старый браузер не поддерживает Service Worker, открытая вкладка продолжает работать офлайн, но перезагрузка без сервера может не сработать.

## Данные и допущения

- **Источник:** шесть строк выпуска, шесть строк качества и четыре простоя за 01–02.10.2026; три месячных плана. Числа сохранены в `app/seed/seed_data.json` без изменений.
- **Синтетическая история:** 60 дней до 01.10.2026, фиксированный генератор seed=42, `is_synthetic=true`. План синтетического дня — 240 единиц. Строки кейса остаются с планом 120; смешение периодов ограничивает интерпретацию прогноза.
- **Смены:** исходные строки не содержат смену, поэтому `shift=0` означает «неизвестна / суточный агрегат», а не первую смену.
- **Оборудование:** состав по заданию; critical, MTBF и даты обслуживания — демонстрационные допущения, `is_demo=true`. Исторические даты ТО заданы до обучающего окна, чтобы не использовать будущие сведения.
- **Простои:** даты и длительности кейса сохранены. Точное начало отсутствует, 10:00 принято технически, `time_assumed=true`. Время создания исторических сигналов тоже условное. Замена фильтра не названа плановой в кейсе и отнесена к unplanned; «Плановое ТО» — planned. Сумма минут машин не равна простою завода.
- **Склады, буферы, текущая смена и контроль:** полностью демонстрационные данные. Начало live-показа — 03.10.2026 12:00, начальные накопленные количества и время работы заданы для наглядности. Номинальная скорость — 15 единиц/час, буферы 24/20/16, один тик = 1/5/20 виртуальных минут. Нет реальной телеметрии.
- **Качество:** дефекты на разных переделах не считаются уникальными автомобилями. Факт сборки 240, годные на сборке 237; финальная приёмка в источнике не дана.
- **План:** сумма моделей 4 800 против цели 5 500. Отдельный `data_warning`. Факт по моделям отсутствует и возвращается как null, без выдуманного распределения. Общий факт 240 — по 02.10.
- **OEE по заданию:** A = часы работы / (16 × количество представленных дней); P = факт / план; Q = годные / выпущено; OEE = A × P × Q. Это демонстрационная методика, поскольку идеальный цикл и период исходных строк не известны. Плановое ТО не порождает аварийный инцидент и не вычитается повторно из уже указанного run_hours. Заводской показатель берётся с минимальной A×P. Live-показатель отдельно оценивает текущий поток по прошедшему времени и загрузке и подписан как оперативная модель.
- **Ручной пример:** Сварка-1 01.10: 7,8/16 × 118/120 × 116/118 × 100 = **47,125%**. При округлении двоичного float итог может отображаться 47,12%; тест допускает 0,01 п.п.
- **Узкое место LIVE:** минимальный эффективный поток годных изделий. Симулятор ограничивает движение доступным входом и местом в выходном буфере. Прогноз заполнения использует текущий рост буфера, не заявляет достоверный срок остановки реального завода.
- **Плановый прогноз:** линейная регрессия по 21 последнему дню, 1000 бутстрэп-траекторий остатков, 23 рабочих дня, 2 учтённых и 21 оставшийся. Сценарные коэффициенты 0,75 / 0,94 / 0,70 заданы вручную и раскрыты в ответе API.
- **Бизнес-эффект:** неплановые 120 минут за два дня экстраполируются на рабочие дни. 18 дефектов означают события исправления на переделах; стоимость брака трактуется как цена одного события, а не списания уникального автомобиля. По умолчанию 150 000 ₸/час оборудования, 80 000 ₸/дефект, 15 млн ₸ внедрение, 250 дней; улучшения 20% и 25%. Получается 52,5 млн ₸/год — сценарная оценка, не обещание экономии. Окупаемость без налогов, дисконтирования и эксплуатационных расходов. При нулевой экономии — null.

## API

Все REST-маршруты имеют префикс `/api`. Ошибки: `{"error":{"code":422,"message":"...","details":[...]}}`. Подробная схема входов доступна в `/docs`.

| Метод | Маршрут | Результат |
|---|---|---|
| GET | `/plant` | Участки, оборудование, связи, live-состояние |
| GET | `/stages/{code}` | KPI кейса, история, инциденты и риски участка |
| GET | `/equipment/{code}` | Статус, обслуживание, простои, риск |
| GET | `/kpi?from=2026-10-01&to=2026-10-02&stage=painting` | Агрегаты; даты по умолчанию — два дня кейса |
| GET | `/dashboard` | План, KPI, причины и приоритеты |
| GET | `/downtime?from=&to=&stage=` | Простои и агрегаты |
| GET | `/quality?from=&to=&stage=` | Качество по дням и участкам |
| GET | `/incidents?severity=&stage=&status=&from=&to=` | Фильтруемый журнал |
| POST | `/incidents/{id}/ack`, `/incidents/{id}/resolve` | Принять / закрыть; повторное принятие закрытого — 409 |
| GET | `/forecast/downtime`, `/forecast/plan`, `/forecast/bottleneck` | Риски, план и буферы |
| POST | `/forecast/refresh` | Пересчёт кэшированных прогнозов |
| GET | `/recommendations` | Рекомендации по незакрытым сигналам |
| POST | `/scenarios/{name}` | conveyor_failure, paint_defect_spike, supply_disruption, reset |
| GET, POST | `/simulation` | `{ "enabled": true, "speed": 20 }`; скорости 1, 5, 20 |
| POST | `/impact` | Параметры улучшений/стоимости, экономия, окупаемость |
| GET | `/timeline?at=2026-10-03T12:00:00` | Снимок на или до момента; виртуальное время без TZ |
| GET | `/health` | Проверка соединения с БД |

Коды участков: `parts`, `welding`, `painting`, `assembly`, `quality`, `finished`. Необязательные query-параметры следует **опускать**, а не передавать пустые даты.

WebSocket `/ws/live`: JSON `{type,payload}`. Типы: kpi_update, equipment_status, incident_created, buffer_update, forecast_update, scenario, heartbeat. Heartbeat каждые 15 секунд; клиент переподключается с задержкой 1–30 секунд. Медленные/отключённые клиенты удаляются из рассылки.

## Структура и эксплуатация

`app/models.py` — SQLAlchemy-схема; `app/services/` — расчёты, правила, симулятор, ML и представления; `app/routers/` — REST и WS; `app/seed/` — исходный кейс и генератор; `app/tests/` — тесты. `frontend/` — HTML, CSS, JS-модули, Service Worker и локальный Inter (лицензия SIL OFL в `frontend/fonts/OFL.txt`). Сборщики и npm не нужны.

Переменные окружения: `DATABASE_URL`, `TICK_SECONDS` (по умолчанию 2,5), `SIMULATION_ENABLED` (true/false). Для PostgreSQL задайте `DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:5432/DB` перед стартом; таблицы создаются теми же моделями без изменения кода. Перенос уже накопленных записей между СУБД отдельно не реализован. Живое подключение PostgreSQL в среде подготовки не проверялось; проверена компиляция схемы для PostgreSQL.

Прототип предназначен для локального показа. Роли, авторизация, TLS, резервирование, миграции схемы и промышленный аудит входят в последующую разработку. Docker Compose публикует порт только на 127.0.0.1.

## Проверки

```sh
python -m pytest app/tests -q
```

Тесты используют временную SQLite и не изменяют демонстрационную базу. Проверяются ручной OEE, качество, идемпотентность seed и правил, границы порогов, исключение планового ТО из аварий, временное разделение признаков ML, диапазоны вероятностей, квантили, API, валидация, WebSocket, каскад буферов, снабжение, снимки и сохранность исходных данных после сброса.

Дополнительные проверки офлайн-модулей (Node 22+, только для разработки; приложению Node не нужен): `node --test app/tests/test_offline.mjs`. Настроен GitHub Actions для Python 3.11/3.12. Локально пройдены 36 Python-тестов и 3 теста JavaScript; визуально проверены все вкладки, карточки, сценарий, фильтры, нулевая экономия и перезагрузка без работающего сервера.

Для подготовки автономного снимка после изменения кейса: запустите сервер, затем `python tools/export_offline.py`. Команда обновляет только встроенный снимок интерфейса и не меняет серверную базу. Для демонстрации используйте снимок из чистого сброшенного состояния.

## Пять направлений развития

1. Реальные источники OPC UA / MQTT: телеметрия, справочник сигналов, контроль качества и задержки данных.
2. 3D-визуализация: привязка к планировке завода и координатам оборудования при сохранении быстрой 2D-схемы.
3. Мобильные алерты: Telegram/e-mail, ответственные, подтверждение получения и эскалации.
4. ML на потоковых данных: разметка отказов, мониторинг дрейфа, калибровка вероятностей и проверка эффекта на временном holdout.
5. ERP/MES: план по VIN/моделям/сменам, реальные буферы, финальный контроль и создание заявок на обслуживание.
